# Professional Self-Assessment

I am finishing my B.S. in Computer Science with a Software Engineering concentration at Southern New Hampshire University. My GPA is 3.966, and I expect to graduate in Spring 2027. I want to work in software engineering, and I am especially interested in red team penetration testing. I also work as a Fractional AI Programming Developer at Rewyndr, a Pittsburgh startup, so a lot of what I learned in class has already been tested in real work. This self-assessment covers my strengths, how the program shaped my goals, and how the three artifacts in this portfolio fit together.

Working with a team is something I do every day. In IT-204, my group analyzed the needs of a fictional client, Birchwood Lane Schools, and recommended a database for its platform. We chose Microsoft SQL Server over IBM Db2. At Target, I am a team leader, and my team works toward freight timelines. At Rewyndr, I am part of the software team, and we work toward software deadlines. The work is different, but the point is the same. A team has to hit a goal together, and that only works if everyone knows what they own.

I have practiced explaining technical work to people who are not technical. In CS-255, we presented platform requirements to a nontechnical audience. At Target, I explain the reasons and methods behind our plans to my team members constantly. At Rewyndr, I explain technical issues to shareholders. One example is telling them we needed to upgrade our EC2 server because it kept erroring out from running out of memory. Shareholders do not need to know how EC2 works. They need to know what is wrong and why the fix is worth it.

In CS-300, we studied many different data structures and algorithms, and we practiced using them and comparing them. That class taught me that picking one is a trade-off, not a right answer. I used that in my Breakout game enhancement. I replaced 77 hardcoded bricks with a vector and a spatial grid, so the ball only gets checked against the bricks near it. The grid costs a little setup and memory, and it saves a lot of collision checks as the level gets bigger.

In CS-360, I planned and engineered the InvenTepsic app, including building its database from the ground up. That gave me my first full view of a project, from the schema to the screens. In IT-204, I worked on relational database design for Birchwood Lane Schools. In CS-340, I worked with MongoDB through PyMongo. Each one showed me a different side of working with data, and the capstone let me go back and make my own earlier work better.

I practiced security through multiple OWASP dependency checks and code reviews. In my own code review of InvenTepsic, I found that the login stored and compared passwords as plain text. I replaced that with salted PBKDF2 hashing. Fixing it changed more of the code than I expected, because I could no longer compare the password inside the SQL query. At Rewyndr, I discovered and fixed endpoints that were missing authorization calls. That is the kind of problem I want to spend my career finding.

The program and this portfolio shaped my goals. Reading my own old code with a critical eye is what stood out most. In every artifact, I found something I could see was not good enough, and I had to decide how to fix it and prove it was fixed. That is a lot like security work, where the job is finding the flaw before someone else does. It pushed me further toward software engineering with a security focus, and toward red team penetration testing.

The three artifacts each cover one of the three categories. InvenTepsic, from CS-360, is my software design and engineering artifact. I added barcode scanning with CameraX and ML Kit and replaced plaintext passwords with salted hashing. The Breakout game, from CS-330, is my algorithms and data structures artifact, with the vector and spatial grid replacing 77 hardcoded collision and draw calls. The Grazioso Salvare dashboard, from CS-340, is my databases artifact. I added input validation, fixed a collection bug, and moved the breed counting into a MongoDB aggregation pipeline.

These three projects share a pattern. Each one started with something in my own earlier work that worked but was not good enough: passwords in plain text, 77 calls typed out by hand, a database call that pulled back every row. Each enhancement fixed a real problem and not a made-up one. I want to be upfront about one limit. I no longer had the dataset or the course environment for the Grazioso dashboard, so I checked those changes by reading the code carefully instead of running it. My instructor noted that I did not claim testing I could not do. I would rather be honest about what I verified than overstate it. The code review video comes first, then each artifact with its narrative, so you can see the original code, the enhanced code, and what I learned from the work.
